# Manual evidence redaction lineage

Refs #285. Accepted M0-D16 requires redaction to create a distinct derived identity while preserving the immutable original; any Contributor may prepare it and a Compliance Lead approves it. This increment records a declared relationship between two already registered artifacts. It does not transform bytes, verify the actual redaction, inspect an upload, release malware, or authorize content disclosure.

Preparation requires current canonical client membership, the fixed Contributor/Compliance Lead/Org Admin preparation permission, and deliberate `evidence_artifact.read` access to both exact artifact resources. Approval requires the fixed Compliance Lead approval permission, a personal HTTP invocation, the same two artifact permissions, the exact prepared revision and an available derivative. Both mutations also retain the existing historical Attest management wall. No role, standing firm access, team or artifact grant is created by a lineage decision. Reads preserve their own current membership and both artifact permissions.

The original may be pending, quarantined or rejected: its registration identity supplies provenance and does not change its state or handling rules. Preparation refuses equal artifact identities or equal content SHA even when metadata differs. A new preparation revision preserves the same original/derived registration pair and invalidates applicability of the previous approval; historical facts remain immutable. Self approval requires an independently approved, exact-source EN-04 waiver. A scope for a nonexistent or mismatched lineage preparation cannot be recorded or approved under the new `evidence_redaction` record type; existing waiver record types retain their existing behavior.

Private persisted source capsules bind artifact/tenant identity, registration event identity, full typed registration SHA, content SHA/length and registration time. A separate safe-tuple digest detects inconsistent replay fields; it is a local consistency check, not external authenticity. The source reader independently verifies the canonical retained artifact registration and lifecycle when a command or read runs. Public lineage views expose only artifact ID, content SHA/length and registration time for each artifact, together with attributed lineage decisions and current bounded state. They do not expose original content metadata, registration event envelopes, registration payload SHA, source physical positions or private capsule digests.

Artifact permissions and authoritative source positions are checked again before a mutation is submitted; lineage writes retain ordinary source OCC. A current read captures source and lineage positions and rejects changes during the read. These are bounded observed-source checks, not a cross-stream atomic snapshot or future disclosure guarantee. `approval_current` describes applicability of the retained approval to the current preparation and the observed available derivative; it never grants artifact access or disclosure authority. Original artifact access and state rules still apply independently.

This is metadata lineage only. Scanner/provider qualification, actual byte transformation and delivery, raw-byte hold/retention enforcement, export/package disclosure and the broader #285 disposition criteria remain open. Synthetic inspection outcomes in unit fixtures establish only the already-existing metadata lifecycle boundary.
